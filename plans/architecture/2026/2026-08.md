## ADR-0001 — Adopt the two-store memory architecture as the default

- **Status:** Accepted
- **Date:** 2026-08-02
- **Domain:** Memory architecture
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

Six memory-ish systems were installed at once — MemPalace, graphify, evolve/Honcho,
`.claude/memory/`, and two newer stores. Every additional store is a competing source of
truth and competing tool-selection pressure: an agent asking "what do we know about X"
had no principled way to choose, and the same fact could live in several places with
nothing saying which was current.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Two stores, split by regenerability | Each fact has exactly one home; the split is mechanical, not a judgement call | Two systems to install and keep running |
| B. One general-purpose store | Simplest to operate | Structure goes stale on every commit and cannot be told apart from durable rationale |
| C. Keep all six, route by convention | No migration | Convention is not enforcement; this was the failing status quo |

### Decision

Two stores, split on **whether the fact can be regenerated from source**:
[codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp) holds structural
truth — call graphs, blast radius, dead code, routes — regenerated deterministically at
zero write cost. [Hindsight](https://github.com/vectorize-io/hindsight) holds experience
— deliberation, rationale, rejected alternatives, outcomes — which nothing can regenerate.
**Ratified** decisions are not experience and do not live there: they are ADRs in
`plans/architecture/`, owned by `repo-memory` (ADR-0004). The bank holds the reasoning
that produced a decision; the ADR holds the decision. They never hold the same fact, share
no identifier, and neither can query the other; the join is performed at query time by
translating identifiers into domain concepts.

**Tradeoff accepted:** two services instead of one, and a cross-store join the caller
must perform by hand. Measured: querying the experience store with identifiers scored the
correct memory at 0.000015 where domain language scored 1.096 — so the join is not
optional, and getting it wrong looks exactly like an empty store.

### Consequences

- **Positive:** structural questions cost nothing and are never stale. Rationale survives
  refactors that rename every symbol involved.
- **Negative:** an agent that skips the translate step gets a useless recall and cannot
  tell that from "nothing recorded". Retaining code structure into the experience store
  silently destroys the architecture and nothing prevents it — the writer is the filter.
- **Follow-on work:** MemPalace retired from routing (data kept); the four MemPalace
  skills scheduled for removal.

## ADR-0002 — Fold memory health into memory-setup and retire memory-onboarding

- **Status:** Accepted
- **Date:** 2026-08-02
- **Domain:** Skills and marketplace
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

`memory-onboarding` and `two-store-memory-setup` both claimed machine-scope memory
verification. The collision was measured, not theoretical: `memory-onboarding`'s first
positive trigger, "is my memory set up right", was the other skill's first *negative*
trigger, fenced apart by hand in a bench fixture. Commit `d7b2500` had already narrowed
one description because the overlap "cost trigger precision". Eleven load-bearing rules
were stated in both skills with no owner.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Retire the aggregator | One owner per rule; removes the trigger collision at its source | Loses a single cross-strata matrix |
| B. Better fences | Smallest diff | Fences are maintained by hand in prose and fixtures, and had already failed once |
| C. Reduce it to a pure router owning no rules | Keeps the entry point | It already claimed to be that and demonstrably was not |

### Decision

Delete `memory-onboarding`. Nine of its eleven checks already had a better owner —
`memory-setup`'s gated Phase 5, `evolve-status`, `repo-kickstart`'s verification
checklist, `repo-memory`. `memory-setup` now states outright that it answers "is my
memory set up right"; verification is Phase 5, not a separate skill.

**Tradeoff accepted:** no single command reports every stratum in one matrix. Health is
answered per-owner instead.

### Consequences

- **Positive:** one owner per rule, one fewer skill competing for "memory" triggers, no
  more hand-tuning two descriptions against each other.
- **Negative:** a user wanting a whole-system view runs two skills. `buhhdy` still names
  the deleted skill in three places and is deliberately untouched pending its removal.

`46889b2`, `plans/development/2026-08-02-memory-skill-migration-plan.md`.

## ADR-0003 — Architecture decision records live in plans/architecture/; OpenSpec writes specifications only

- **Status:** Accepted
- **Date:** 2026-08-02
- **Domain:** Planning and specs
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

Three ADR locations were in play at once. `plans/architecture/NNN-<slug>.md` was **live
and automated** via `promote-adr.ts`, driven by `openspec-conformance` at archive time
and `pr-shepherd` at close-out. `docs/adr/NNN-title.md` was prescribed in two places —
`AGENTS.md:267` and the operator's machine-level policy — and **the directory did not
exist**. A third was proposed. Meanwhile OpenSpec, a specification tool, owned ADR
promotion, which conflated "what we will build" with "what we decided and why".

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. `plans/architecture/`, OpenSpec writes specs only | Keeps the live location; separates specification from decision; ADRs are documents and `plans/` is for documents | Requires retargeting `promote-adr.ts` and correcting two prescriptions |
| B. `docs/adr/` as prescribed | Matches the widely published convention and the existing written policy | The directory never existed; would abandon a working pipeline for a greenfield one |
| C. Split by origin | No pipeline change | Two ADR stores; "which one" becomes a judgement call on every decision |

### Decision

`plans/architecture/` is the single ADR store, organised as a master `DECISIONS.md`
indexed by domain, a per-year `INDEX.md` decision log, and one detail file per month.
**OpenSpec does not own or write ADRs** — it writes specifications for features and
development work. `promote-adr.ts` is retargeted at the new structure and its ownership
moves to `repo-memory`.

**Tradeoff accepted:** one file per *month* rather than the one-file-per-ADR convention
every published source assumes. That costs per-ADR git-history granularity and
compatibility with `adr-tools`-style tooling. Bought back by keeping globally sequential
IDs, append-only records within each file, and supersede-by-ID across files.

### Consequences

- **Positive:** one location, and `plans/` holding decision *documents* is the existing
  hard rule working rather than an exception. Specification and decision stop being
  conflated.
- **Negative:** `AGENTS.md` and the operator's machine-level policy both said `docs/adr/`
  and must be corrected, or agents will keep writing to a directory that does not exist.
- **Follow-on work:** retarget `promote-adr.ts`; update repo conformance to require the
  structure.

### Related

`skills/repo-memory/`, `skills/openspec-conformance/promote-adr.ts`,
[../TEMPLATE.md](../TEMPLATE.md).

## ADR-0004 — repo-memory owns ADRs; all other memory defers to the two stores

- **Status:** Accepted
- **Date:** 2026-08-02
- **Domain:** Memory architecture
- **Confidence:** Medium
- **Supersedes:** None
- **Superseded by:** None

### Context

`.claude/memory/` held twelve records that were mostly experience — preferences,
corrections, past outcomes — which is exactly Hindsight's content. The repo said two
contradictory things one file apart: `AGENTS.md` §Repo Memory instructed agents to
*"check `.claude/memory/` first"*, while the same file and `repo-kickstart/reference.md`
called it *"retired from routing"*. A SessionStart hook actively injected the read-first
instruction. Both were live.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. repo-memory becomes the ADR skill; everything else to the two stores | Gives the skill a job nothing else does; resolves the contradiction by narrowing scope | Existing records need triage |
| B. Keep repo-memory as committed experience memory | Works with no server, reviewable in a PR, travels with a clone | A second per-repo experience store — the duplicate-source-of-truth this architecture exists to prevent |
| C. Delete repo-memory entirely | Fewest moving parts | Strands the twelve records and loses server-free, PR-reviewable decision history |

### Decision

`repo-memory` owns architecture decision records at `plans/architecture/` — their
format, numbering, indexes and lifecycle — and nothing else. Structure defers to the code
graph, experience to the Hindsight bank. `.claude/memory/` is retired for new writes;
existing records are triaged rather than deleted.

**Tradeoff accepted:** committed, server-free, PR-reviewable memory now covers *only*
ratified decisions. Anything not decision-shaped requires Hindsight to be running to be
recalled at all.

### Consequences

- **Positive:** the read-first/retired contradiction is resolved by giving the store one
  narrow, defensible job. ADRs remain reviewable in the PR that changes them.
- **Negative:** a contributor without Hindsight installed loses recall of everything that
  is not an ADR. The twelve existing records still need triage and are not migrated by
  this decision.
- **Follow-on work:** correct `AGENTS.md` §Repo Memory; triage the twelve records; decide
  the SessionStart hook's fate.

`skills/repo-memory/`, `AGENTS.md` §Repo Memory, ADR-0001.

## ADR-0005 — Prove a skill refinement pairwise against a champion, not on absolute judge scores

- **Status:** Proposed
- **Date:** 2026-08-02
- **Domain:** Tooling and CI
- **Confidence:** Medium
- **Supersedes:** None
- **Superseded by:** None

### Context

`skill-bench.ts` scores each response in isolation against a rubric, 1–5, median over
runs, appended to the append-only ledger `tests/bench/history.jsonl`; `skill-trends.ts
regressions` reads that ledger and flags a latest run worse than the one before it. That
answers *did this run get worse* but not *is this version of the skill better than the
one it replaces* — absolute scores compress (most land 3–4) and drift across judge-model
versions, so a one-point move means nothing across a version boundary.

The pressure is the authoring-standard plan's Task 8: retro-fit every repo skill to the
new standard, in dependency order, as dozens of small PRs. Each of those PRs needs a
per-skill "this is not worse than what it replaces" gate that a reviewer can trust
without re-reading every output. The existing objective gates — asserts, the token-ratio
budget, and the pass-rate/1.1×-token champion check drafted as PR #47's R3 — cover
correctness and cost but say nothing about output quality, which is exactly the axis a
refinement is meant to move.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Objective gates first, position-swapped pairwise battle second, humans last | Comparative verdicts survive judge-model drift; reuses the existing session-driving and caching paths; the judge only ranks what already passed the measurable gates | A second persisted artifact tree; one extra judge call per battled scenario; needs a champion lineage that does not exist yet |
| B. Keep absolute 1–5 scores, raise the threshold | No new machinery | Thresholds on a compressed, drifting scale are noise; cannot compare across versions, which is the whole question |
| C. Human review of every retrofit PR | Highest fidelity | Does not scale to a repo-wide retrofit; the reviewer becomes the bottleneck for dozens of PRs |
| D. Adopt `autoevals` calibrated scorers now | Maintained, calibrated, includes a Battle scorer | Speaks the OpenAI SDK, so judging with Claude needs a compatible endpoint; adopting a dependency before the local schema has settled |
| E. Do nothing | Zero cost | Task 8 proceeds with no quality gate, or does not proceed |

### Decision

Skill quality is evaluated in a fixed order — **objective gates first, judge second,
humans last**. The judge never opines on anything measurable: asserts, budget ratios and
the champion pass-rate/token check decide first, and only variants that already pass them
are ranked. Ranking is **pairwise**: the working-tree skill (challenger) and the champion
are run over the same scenarios, judged twice with the positions swapped, and a verdict
counts only if both orders agree after un-swapping; disagreement, and any verdict the
judge cannot ground in a verbatim quote from each side, records as `TIE`. Outputs persist
under `tests/bench/outputs/` keyed by (prompt hash, skill content hash) so an unchanged
champion costs nothing across revise-and-rebattle cycles; every judged pair appends to
`tests/bench/battles.jsonl`, and only the per-skill tally lands in `history.jsonl` so
`skill-trends.ts` stays the single query layer.

Two thresholds, for two different consumers. **Non-regression** — the Task 8 retrofit
gate — requires wins ≥ losses among decided scenarios, with all-ties passing as
not-worse. **Superiority** — required before declaring a challenger better or replacing a
champion — requires ≥5 decided scenarios and ≥70% wins; below that floor the tally is
reported and nothing is declared.

**Tradeoff accepted:** a bench at the standard's minimum size (~2 battle-eligible
scenarios) can satisfy non-regression but can never reach superiority. Most skills will
therefore be held to a weak floor until someone grows their scenario set — deliberately,
because the alternative is letting a two-scenario sample declare a winner.

### Consequences

- **Positive:** refinements are comparable across judge-model versions, which absolute
  scores are not. The retrofit gets a gate that scales to dozens of PRs. Every verdict
  stays re-inspectable and re-judgeable from the persisted outputs and the log.
- **Negative:** judge cost roughly doubles on each battled scenario (the position swap),
  mitigated only by the tie short-circuit. Two git-tracked artifact trees grow
  monotonically and nothing prunes them. Verdicts are valid only within a fixed scenario
  set — editing a bench file invalidates the comparison against the existing champion.
  Most benches cannot claim superiority at all, so "better" stays a human judgement in
  practice for a while. And the whole mechanism is blocked: it builds on
  `championRow`/`beatsChampion`, which are not in `scripts/skill-bench.ts` and whose
  PR #47 is not open, so Task 8 cannot start.
- **Follow-on work:** land the champion-lineage gate before implementing battle mode;
  generate `plans/development/skill-retrofit-order.md`; decide a retention policy for
  `tests/bench/outputs/` before it is committed at scale. Escalation panels, `--review`
  human adjudication, per-axis rubrics and distractor-present battles are deferred — the
  persisted-output and `battles.jsonl` schemas are the contract they build on.
